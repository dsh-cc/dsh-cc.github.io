# 记忆体系

本文写给希望 agent 跨会话记住事情的人：项目约定、你的反馈、关于代码库的
事实。dsh-cc 提供两个互补的层——一个每个会话都会加载的 `CLAUDE.md` 约定
文件，以及一个持久的、基于文件的 **memdir**（`MEMORY.md` 加主题文件），
agent 通过专用的 `memory_save` 通道写入，并通过动态召回读回。

## 两层概览

| 层 | 内容 | 谁写入 | 何时加载 |
| --- | --- | --- | --- |
| `CLAUDE.md` | 项目约定、构建命令、代码风格 | 你（由 `/init` 脚手架生成） | 每个会话 |
| memdir（`MEMORY.md` + 主题文件） | 持久事实：用户偏好、反馈、项目与参考笔记 | agent，通过 `memory_save` | 主题目录每个会话都在；主题正文按需召回 |

记忆层支持 `CLAUDE.md` 风格的上下文，外加一个专用的持久记忆写入通道。
记忆按工作区隔离，并支持可选的共享团队记忆。

## CLAUDE.md 层

`CLAUDE.md` 是约定文件：你希望在该仓库的每个会话中都生效的持久、人工编写的
指令——构建命令、代码风格、仓库特有规则。它位于仓库根目录，每个会话都作为
上下文挂载。

运行 `/init` 即可脚手架生成。根据兼容性矩阵，dsh-cc 中的 `/init` 会驱动一个
后续模型轮次来写入或刷新 `CLAUDE.md`，而不是 Claude Code 上游的一次性初始化
流程（状态：partial）。之后你可以像编辑普通 Markdown 文件一样手工编辑它。

一个上游特性没有移植：`CLAUDE.md` 的 `@path` 导入机制缺失——目前没有解析器
或加载器处理导入。

## memdir 层

memdir 是持久存储。它的布局：

- **记忆主目录**（默认为 harness home 的 `memory/`）充当所有工作区共享的
  **全局层**。
- 每个 git 仓库在 `<memoryHome>/projects/<slug>/` 下有自己的工作区目录——
  链接的 worktree 与子目录会先折叠到主检出上（`canonicalMemoryRoot`），因此
  它们共享同一个存储。会话转录仍按原始 cwd 分组；对 worktree 会话，记忆不再
  跟随这种分组。
- 每一层都有一份 `MEMORY.md` **策展索引**（上限 200 行 / 25 KB），每行索引一个
  `.md` **主题文件**。该文件本身留在磁盘上，从不原样进入提示；它贡献的是顺序——
  提示中的目录先列出它指向的主题，顺序即该文件自身的顺序。
- 每个主题文件带有 `name`、`description` 和 `type`（`user` / `feedback` /
  `project` / `reference`）frontmatter，以及一个 Markdown 正文。

不同仓库的会话永远不会看到彼此的私有记忆；对所有工作区都有用的事实以
`scope: "global"` 保存。

### 提示里实际携带的内容

`memory` 系统提示段渲染的是**一份**带作用域标记的目录，覆盖每一层已解析的主题
文件：一个 `## Memory index` 标题、每主题一行（带描述），以及 grep 搜索指引。
`MEMORY.md` 本身对提示不可见——其中的策展文字，以及目标没有可解析主题文件的
指针行，都留在磁盘上——但它的指针顺序是目录的排序输入：索引列出的条目排在最前，
按该文件自身的顺序，并按 workspace → team → global 轮转交错；其余主题接在后面，
每个作用域按文件名排序。轮转交错是排序上的公平，不是可见性保证——一旦开始丢弃
条目，某个作用域仍可能整个从目录里消失。目录只给出主题的名字，正文由召回注入。

预算由 `cc-memory-section` 设置命名空间控制，默认开启，且每次渲染都会重新读取
——一次设置写入对下一次组装生效：`truncate` `true`（设为 `false` 时目录完整
渲染，且永远不会移除该段）、`max-bytes` `24576`（1024..65536，是整个目录块的
上限，含标题与省略行）、`description-max-bytes` `160`（0，或 8..1024；`0` 关闭
描述裁剪，1-7 会被拒绝）。非法值整段拒绝，从不钳制进范围。超预算时，整条条目从
交错顺序的底部开始丢弃（绝不截半行），末尾的省略行会统计被略去的主题数；当连
一条条目都放不下时，只渲染标题与这一行。完整键表见
[/reference/settings](/zh/reference/settings)。

`memory` 系统提示段始终会渲染——没有记忆的层会显示一个占位符——因此保存
指引不会消失。被委派的 subagent 子代理将这一段渲染为空，该段便从它们的提示
中消失；子代理需要的事实必须由父级提示传递。

### `memory_save` 通道

agent 唯一可用的保存通道是 `memory_save` 工具。记忆目录位于所有会话工作区
之外，直接针对它们的 `write`/`edit` 调用会被 fs 沙箱拦截并总是失败——系统
提示中明确说明了这一点。`memory_save` 接收结构化字段（`name`、`type`、
`description`、`body`，可选 `scope`：`workspace`（默认）或 `global`），从调用
agent 的规范化 git 根解析目标目录，在 host 侧生成 frontmatter，并更新
`MEMORY.md` 指针。

::: info
`memory_save` 只写工作区与全局两层；团队范围的保存通道和删除通道均为后续
工作。注册是机会性的：没有工具服务的 host 保持只读。
:::

### `/memory`

面向用户的 `/memory` 命令列出记忆文件，或按名称打印某条记忆的正文。它注册为
全局命令，因此运行时不需要模型轮次。

| 输入 | 结果 |
| --- | --- |
| `/memory` | 按名称排序，以 `- name (type) — 首行` 的形式列出每个主题，并附记忆目录头。 |
| `/memory <name>` | 打印单条记忆的 frontmatter 与完整正文，按 frontmatter `name` 或文件名匹配。未知名称会给出友好提示。 |

它完全只读，斜杠输入与输出不会出现在模型请求中——使用它不消耗模型 token。

### 用 `/learn` 蒸馏失败

`/memory` 用来查看记忆，`/learn` 则用来写入记忆：该命令扫描持久的会话转录，
找出反复出现的“失败→修正”模式，并将其蒸馏进工作区记忆。默认是 dry-run——
它只渲染排序后的发现和提议的记忆块，什么也不写。只有 `/learn apply` 会写入：
它创建 `session-learnings` 记忆主题，作为一个由 `/learn` 完全拥有、每次 apply
时整体重新生成的 managed marker block——其他地方手工写的记忆不受影响——并
更新 `MEMORY.md` 指针。发现为空时，现有记忆保持原样。`/learn all` 扫描所有
项目的会话而不只是当前工作区；`/learn days=N` 覆盖时间窗口（默认 14）。调优
在 `cc-learn` 设置命名空间：`enabled`（默认 `true`）、`days`（默认 `14`）、
`min-occurrences`（默认 `2`）。

## 自动整合

记忆维护在后台运行，从不阻塞你的会话。记忆层用一个索引门控约束
`MEMORY.md` 的写入；当索引压力累积时，会写入一个 `.consolidation-needed`
标记，并把一次强制的「dream」排入队列。

整合包（`dsh-memory-consolidation`）还提供轮次结束抽取：一个只带读/搜索
工具的后台 fork subagent 把本轮的持久事实抽取为结构化输出，由插件校验并在
host 侧写入——fork 本身没有任何写工具，沙箱会话因此永远无法直接写记忆。来自
并行会话的并发抽取不再互相丢弃对方的 `MEMORY.md` 指针：索引写入会对照该任务
读取时的基线做检查，并在其间落地的改动之上重新应用——主题文件正文仍是后写者
胜，dream 锁只用于串行化整合。

Dream 整合则是一个只读的 fork subagent，它回顾过去的会话并报告重写后的
`MEMORY.md` 与主题文件集合，同样由插件落地。只有三个门全部通过时它才会
运行：

1. **时间**——距上次整合至少 `minHours`（默认 24）。
2. **会话数**——至少 `minSessions`（默认 5）份新转录。
3. **锁**——`.consolidation-lock` 文件保证互斥；持有超过 `lockStaleMs`
   （默认 1 小时）的陈旧锁会被回收，整合中途崩溃也能自动恢复。成功的整合会
   释放锁（清空持有者、保留 epoch），下一次 dream 只需等待自身的冷却或时间门；
   失败或被杀的整合则回滚锁，让时间门重新打开。

另有两个配置项约束强制路径：`pressureCooldownMinutes`（默认 60）是两次
强制（压力）dream 之间的最小分钟数，`sessionsRoot`（默认
`<DSH_HOME>/sessions`）是这些门控扫描的会话存储根目录。

## 召回：记忆如何在后续会话浮现

你不需要主动索取记忆。一个 `agent/pre-step` 监听器会运行一次**小模型侧查询**
（一个 fork 出的 subagent），询问哪些主题文件与当前轮次相关，然后将它们的
正文注入上下文：

- 召回扫描两层（agent 的工作区目录加全局层）并去重：本会话已展示过的主题
  文件不会再次注入。
- 会话中早前使用过的工具会被跟踪，正在活跃使用的工具的 reference-doc 类
  记忆会被抑制——关于它的警告和坑仍然会浮现。
- 召回可通过 `recallEnabled`（默认 `true`）关闭；设置
  `recallUseSmallFast: true` 可让召回 fork 走廉价通道。缺少 subagent 服务或
  provider 时召回静默跳过，不报错。

::: tip
召回侧查询依赖一个已注册的一次性 subagent provider；memory 包本身不附带
provider（组合 `fork` 或 `spawn` 即可）。
:::

### SystemOne 召回决策（可选开启）

上面的侧查询可以换成逐候选判定：把 `cc-systemone-memory-recall` 命名空间设为
`shadow` 或 `active` 后，SystemOne 决策模型会针对每个候选回答一个相关度问题并
返回独立的概率，再由一个确定性的过滤器决定注入哪些——概率大于等于
`include-probability`（`0.75`）是明确纳入，小于等于 `exclude-probability`
（`0.25`）是明确排除。生成式选择器仍然保留，作为回退。

| 键 | 默认值 | 含义 |
| --- | --- | --- |
| `mode` | `off` | `off`：只走旧选择器，不读路由、不发请求；`shadow`：旧选择器照常选择并注入，只记录对比结果；`active`：由决策模型决定 |
| `timeout-ms` | `1500` | 100..30000；整轮选择的时限（24 个候选一批约 1.3 秒） |
| `max-input-tokens` | `6000` | 512..16000；单批请求预算 |
| `max-candidates` | `96` | 1..256；候选池更大时回退到旧选择器 |
| `batch-size` | `24` | 1..32；同时受路由声明的问题数约束 |
| `fallback-max-candidates` | `256` | `max-candidates`..1024；超过它则跳过本轮召回，而不是从子集里挑 |
| `fallback-max-bytes` | `65536` | 4096..262144；旧选择器收到的文本的 UTF-8 上限 |

在 `active` 模式下，概率严格落在两个阈值之间会让整个候选池变得不确定，回退到旧
选择器一次——其他各种退化情形（没有服务、路由无法解析、超过候选上限、批次或
token 预算溢出、超时、答案格式错误）同样只回退一次。取消从不回退，候选全部低
概率是一个合法的空结果。

启用它需要**同时**具备两个条件：决策服务已挂载，且模式不是 `off`。只有服务而
模式不变，什么也不会发生；只有模式而没有服务，只会一路回退。
`recallEnabled: false` 依然会关掉召回——连同这三种模式；而
`recallProviderName`、`recallAgentOptions` 与 `recallUseSmallFast` 只配置旧选择器
及其回退。

隐私：决策路由收到的只有本轮查询加候选元数据（每个候选的作用域、文件名、名称与
描述，以及本轮已用过的工具名）。文件内容、绝对路径、内容哈希与工具参数从不发送；
答案也无法扩大访问权限——被选中但在重读时哈希已变的文件会被丢弃，而不是注入。

### SystemOne 抽取门控（可选开启）

上文描述的轮次结束抽取也可以用同样的方式加一道门控：把
`cc-systemone-memory-extraction` 设为 `shadow` 或 `active` 后，一次针对完整回顾
窗口（上次已回顾 seq 之后的事件，加上现有主题索引）的调用只回答一个问题——这个
窗口里是否至少有一条持久的新事实？只有明确的低概率判定才可以省略抽取 fork；其他
任何结果都照旧抽取（窗口不完整、预算溢出、路由或 runner 缺失、答案非法、超时）。

| 键 | 默认值 | 含义 |
| --- | --- | --- |
| `mode` | `off` | `off`：走旧监听器，不发请求；`shadow`：任务经协调器串行化，仍然抽取，只记录本该跳过的判定；`active`：符合条件的低概率判定可以跳过 fork |
| `timeout-ms` | `1500` | 100..5000；单次决策的线上超时 |
| `max-input-tokens` | `6000` | 512..16000；单份决策状态的估算预算 |
| `max-surface-events` | `64` | 1..256；超过它则直接抽取 |
| `max-state-bytes` | `32768` | 4096..131072；完整状态的 UTF-8 预算 |
| `skip-probability` | `0.05` | 0..0.20，两端包含；`p` 小于等于它才可跳过，`0.5` 是固定的正判定边界 |
| `audit-every-n-skips` | `20` | 1..1000；每第 N 次符合条件的跳过会改为一次审计抽取 |
| `failure-cooldown-ms` | `30000` | 1000..300000；失败窗口重试前的等待时间 |
| `session-state-cap` | `200` | 1..2000；无进行中任务的空闲会话状态的 LRU 上限 |

任何一个非法值都会整段拒绝，并保留上一份快照。这些概率是实验性的——不保证准确率
或收益——除非决策服务已挂载，否则门控处于惰性状态：没有它，每个符合条件的窗口照
常抽取。它的披露面比召回的候选元数据更宽：完整窗口会把当前会话文本连同主题索引
一起发送；模式为 `off` 时什么也不发送，而需要裁剪的窗口会被标记为不完整，改为跑
原来的 fork。Shadow 并不与旧调度逐事件一致——它把任务串行化，并且只有在 host
校验并写入该批次后才推进回顾水位，因此未完成的任务永远不会被当成已完成——而
`off` 与 `shadow` 产出的记忆内容与权限完全相同。

## 团队记忆（可选开启）

当 `teamEnabled` 为 `true` 时，一个按工作区共享的团队目录
（`<workspaceDir>/team`）会叠加在工作区私有 memdir 之上，`memory` 段渲染
工作区 + 团队 + 全局的合并提示。它**默认关闭**：启用它会改变持久化的记忆
布局和模型的写入目标，并使团队记忆读取指向一个共享目录。

来源对安全边界说得很明确：按访问的校验链会阻断路径穿越（键名清洗、末段
symlink 拒绝、resolve + 包含检查），但中间路径组件的 TOCTOU 窗口没有完全
闭合。不要在多租户或不可信写入者的部署中启用 `teamEnabled`——它面向
单租户、可信写入者的项目。

## 实用卫生

- 把稳定的项目约定（构建命令、风格规则）放进 `CLAUDE.md`；把逐条的知识
  （用户偏好、反馈、工具的坑）通过 `memory_save` 保存，以便被索引和召回。
- 记忆要保持持久而非临时：主题文件在被取代之前会在后续会话中反复注入，
  因此临时任务状态不属于这里。
- 只对确实对每个仓库都有用的事实使用 `scope: "global"`——工作区记忆保持
  在该仓库的存储内，对外不可见。
